# AI 비서 — 수정 권한 설계서 (로드맵 17단계 후보)

작성 2026-08-21 · 요청: "프로젝트 권한 있는 사람이 스케줄을 이렇게 바꿔줘 → 두뇌가 판단하고 수정"

## 결론부터

**새 엔진을 만들 필요가 없다.** `complete_task`(v29.61)가 이미 정답 패턴이다:
`direct: true` + `resolve()`(찾고 확인 카드 문구 만들기) + `commit()`(사람이 누른 뒤 저장).
이 설계서는 그 패턴을 **날짜·상태 변경 계열로 넓히고**, 그 앞에 **권한 문지기**를 세우는 일이다.

지금 상태: 등록된 행동 17개 중 **수정은 `complete_task` 하나뿐**. 나머지는 전부 `create_*`(폼 프리필).

## 왜 지금 하나

부장님이 원하는 문장은 이런 것들이다:
- "SJE2026-001 마감을 3월 말로 미뤄줘"
- "리뉴시스템 프로젝트 진행률 80으로 올려줘"
- "이 업무 담당을 김대리로 바꿔줘"

지금은 전부 **화면을 찾아 들어가 손으로** 해야 한다. 그런데 데이터는 이미 AI가 읽고 있고
(`query_state`), 확인 카드 기계도 있다. 빠진 건 **쓰기 행동 정의 + 권한 판정**뿐이다.

## 무엇을 만드나 — 행동 3개로 시작

작게 시작한다. 셋 다 `direct: true` + 확인 카드 필수.

| 행동 | 무엇 | 대상 컬렉션 |
|---|---|---|
`update_project_schedule` | 프로젝트 시작/마감일 변경 | `projects` |
`update_project_status` | 상태·진행률 변경 (active/hold/done, progress 0~100) | `projects` |
`reassign_task` | 업무 담당자·마감일 변경 | `tasks` |

**절대 넣지 않는 것**: `wbsData` 쓰기 (CLAUDE.md 금지 조항 — 2026-07-17 WBS 덮어쓰기 사고).
NCR/CAR 발행·삭제도 이 단계에서 제외 (품질 문서는 사람 손으로).

## 권한 문지기 — 이 설계의 핵심

부장님 요청의 "**권한이 있는 사람이**"가 여기다. 세 겹으로 막는다.

### 1겹 — 판정 함수 (새로 만든다)

**조사 결과(2026-08-21 실측)로 확정된 재료**: 로그인 사용자는 `getU(state.currentUser)` 로 얻고,
필드는 `{ id, name, dept, title, role }` (role 값 예: `'user'`). 프로젝트의 `pm` 은 uid 문자열
(`RWqHYJnIdmXWGj9gtCBu3yIkFAn1` — 부장님 uid 와 같은 모양) 이라 `me.id` 와 비교하면 된다.

```js
// ai-assistant.js 안. 화면 데이터로 판정 — 서버 왕복 없음.
function canEditProject(proj) {
  var me = (typeof getU === 'function' ? getU(state.currentUser) : null) || {};
  if (!me.id) return { ok: false, why: '로그인 정보를 읽지 못했습니다 — 새로고침 후 다시 시도해주세요' };
  if (me.role === 'admin') return { ok: true, why: '관리자' };
  if (proj.pm && proj.pm === me.id) return { ok: true, why: '이 프로젝트 PM' };
  // PM 이 아니면 거부하고, 누구에게 요청해야 하는지 알려준다
  var pm = (state.users || []).find(function (u) { return u.id === proj.pm; });
  return { ok: false, why: pm
    ? ('이 프로젝트의 PM은 ' + pm.name + '님입니다 — PM 또는 관리자만 일정을 바꿀 수 있습니다')
    : '이 프로젝트의 PM 또는 관리자만 일정을 바꿀 수 있습니다' };
}
```

- **거부는 친절하게**: "권한 없음"으로 끝내지 말고 *누가 할 수 있는지*를 알려준다
  (예: "이 프로젝트 PM은 홍길동 부장입니다 — 요청하시겠어요?").
- 판정은 `resolve()` 안에서 한다. 권한이 없으면 **확인 카드를 아예 만들지 않는다.**

### 2겹 — 확인 카드 (기존 기계 재사용)

`resolve()`가 `cardLines`를 돌려주면 채팅에 카드가 뜨고, 사람이 버튼을 눌러야 `commit()`이 돈다.
카드에는 **바뀌기 전 → 후**를 나란히 적는다:

```
프로젝트: SJE2026-001 리뉴시스템 기존설비 개선작업
마감:  2026-03-31  →  2026-04-30
       (PM: 김철우 · 내 권한: PM)
[일정 변경]  [취소]
```

### 3겹 — Firestore 규칙 (서버가 최종 판단)

**⚠️ 조사 결과 — 이 부분이 이 설계의 가장 중요한 발견이다.**

```
firestore.rules:55  match /projects/{pid}  { allow read, write: if isCompanyUser(); }
```

**지금 규칙은 사내 로그인 사용자 전원에게 프로젝트 쓰기를 허용한다.** PM 제한이 서버에 없다.
즉 위 1겹(화면 판정)은 **편의일 뿐 보안이 아니다** — 브라우저 콘솔로 우회하면 누구나 쓸 수 있다.

이건 AI 비서 때문에 생긴 문제가 아니라 **원래 그런 상태**다(사람도 지금 그렇게 할 수 있다).
그래서 판단이 필요하다. 두 길:

- **길 A (권장·작다)**: 규칙은 그대로 두고, AI 비서에만 PM 판정을 건다.
  근거: 지금도 사람은 아무 프로젝트나 고칠 수 있고 그게 회사의 운영 방식이다.
  AI 는 "실수로 엉뚱한 프로젝트를 고치는 것"을 막는 게 목적이므로 화면 판정으로 충분하다.
  대신 **17-d 변경 기록을 필수로** 만든다 — 누가 무엇을 바꿨는지 남는 게 실질적 통제다.
- **길 B (엄격·크다)**: `projects` update 를 PM·관리자로 제한하도록 규칙을 고친다.
  ⚠️ 사람이 쓰는 기존 화면들이 같이 막힐 수 있다(WO 자동등록, 진척 갱신 등).
  이건 AI 단계가 아니라 **별도 과제**로 다뤄야 한다 — 여기 끼워 넣으면 서비스가 깨진다.

**제안: 길 A 로 가고, 길 B 는 별도 항목으로 로드맵에 적어둔다.**
⚠️ 규칙을 고치기로 하면 CLAUDE.md 규칙대로 **저장소 + Firebase 콘솔 양쪽 동시 갱신**.

## 파이스에서 가져올 교훈 (코드가 아니라 구조)

파이스를 만들며 값을 치른 것들. 여기 맞게 번역하면:

**① 위험한 행동엔 자동 만료를 붙인다.**
파이스는 아이폰 조작 권한에 30분 만료를 걸었다(켜둔 걸 잊는 게 진짜 위험).
→ 여기서는 굳이 필요 없다(매 요청마다 확인 카드를 누르므로). 다만 나중에
"확인 없이 바로 수정" 모드를 만들 생각이 든다면, **그때는 만료가 필수다.**

**② 되풀이 호출을 막는다.**
파이스는 부서가 같은 도구를 같은 인자로 두 번 부르면 거부한다(상한 8회를 헛되게 태운 사고).
→ 여기서도 `resolve()`가 같은 문서에 같은 값을 쓰려 하면 "이미 그 값입니다"로 끝낸다.

**③ 실패는 원인을 말한다.**
"수정 실패"로 끝내면 사람이 못 고친다. 권한·못 찾음·중복·규칙 거부를 구분해 답한다.

**④ 안전장치는 검사에 못박는다.**
파이스는 울타리를 셀프체크 36항목에 넣어, 나중에 코드를 고치다 무너지면 커밋이 막힌다.
→ 여기서는 `test/` 에 순수 함수 테스트를 넣는다: `canEditProject()`·날짜 검증·중복 판정.
`node test/tool-calc.test.mjs` 처럼 돌 수 있게. **이게 없으면 이 단계는 완료가 아니다.**

**⑤ 스키마만 만들고 실행부를 빼먹지 않는다.**
파이스가 실제로 그랬다(도구 설명은 등록됐는데 실행 코드가 없어 조용히 무시됨).
→ 행동 하나를 추가할 때 `resolve`+`commit`+테스트를 **한 커밋에** 넣는다.

## 17-c — 보류 (다음에 두고 보고 결정)

### 조사로 확정된 사실

**① 규칙은 사내 전원에게 열려 있다.**
`firestore.rules:55` `projects` · `:71` `tasks` 모두 `allow read, write: if isCompanyUser()`.
즉 화면·AI 판정은 **편의이지 보안이 아니다**(콘솔로 우회 가능). AI 때문에 생긴 게 아니라 원래 상태.

**② 규칙을 조이면 같이 막히는 것** — `projects` 쓰기 경로 15곳 전수 조사 결과, 위험 순서:

| 걸림돌 | 왜 위험한가 |
|---|---|
`reconcileProjectProgress()` | **로그인한 모든 사용자**가 **모든 프로젝트**에 대해 실행(2359·2417). `.catch(() => {})` 로 **조용히** 실패 → "진행률이 안 맞는데 이유를 모르겠다" |
`migratePendingRefs()` | 사전등록 계정 첫 로그인 시 그 사람이 걸린 모든 프로젝트 갱신(2581) |
WO 자동등록 | 프로젝트 생성·일정 갱신(1473·1481). `create` 막히면 자동등록 정지 |
`toggleHideProj()` | 프로젝트 숨김 — **화면에도 권한 검사가 없다**(4706). 지금 전 직원이 아무 프로젝트나 숨길 수 있음 |

**③ 플랫폼의 권한 모델은 이미 '개인 3단계'다.** (부장님 지적으로 발견 — 설계서 초안이 틀렸다)
```
관리자(super/exec) └ PM 본인 └ 프로젝트 멤버(projects.members = {부서id:[uid,…]})
```
기존 함수 4개가 전부 개인 조건을 포함한다:
`canEditWbsMaster` · `canProposeWbsChange` · `canManageProjectMembers` · `canEditSchedule`.
`영업부` 는 그 안에서 "프로젝트 관리 권한자"로 이미 처리돼 있다 —
**부서를 별도 조건으로 꺼내면 개인 사다리에 조직 기준을 억지로 끼우는 것**이 된다.
→ 설계서 초안(및 중간에 내가 제안한 "PM + 관리자 + 영업부")은 폐기.

**④ PM 은 항상 채워진다.** 프로젝트 생성 경로 4개 전부 `pm` 을 설정(드롭다운 / 등록자 / 메일에서 찾은 PM).
PM 이 빈 프로젝트가 생길 경로가 없다 → PM 기준 판정은 모든 프로젝트에서 성립.
단 **사전등록 계정(`pu_…`)이 PM 이면** 그 사람이 첫 로그인할 때까지 관리자만 수정 가능
(로그인하면 `migratePendingRefs` 가 실제 uid 로 바꿔 정상화).

**⑤ 부서별 진행사항은 이미 결재 절차가 있다.** (부장님 설명 → 코드 확인)
```
부서 담당자가 WBS 수정 → master(wbsData) 아니라 개인 사본 wbsPending/{pid}_{uid} 에 저장
  → 수정 감지 시 자동 상신 → 결재선: 작성(담당자·자동승인) → [검토(부서장)] → 승인(PM)
  → PM 승인 후 master 반영
```
(`modules/projects/wbs.html` v29.12 shadow 모드 · `_submitShadowApproval()`)

### 그래서 정해진 것 (되돌리지 말 것)

- **부서별 진행사항(`wbsData`)은 AI 가 관여하지 않는다.** CLAUDE.md 금지 조항 + 2026-07-17 사고.
  **결재 상신을 AI 가 대신 올리는 것도 금지** — 결재선의 `작성` 칸이 자동 승인이라,
  AI 가 올리면 사람이 검토하지 않은 내용이 담당자 서명으로 PM 에게 간다.
  (17-b 의 "WBS 진척률은 자동 계산" 거부가 우연히 이 경계를 이미 지키고 있다)
- **`members`(팀) 수정도 AI 관여 안 함.** 화면에서도 멤버는 직접 편집이 아니라 PM 결재 대상이다.

지금 AI 는 `judgeEditProject`(관리자+PM)를 쓰고, 화면은 `canEditSchedule`(관리자+영업부+개별권한+PM)을 쓴다.
한쪽이 다른 쪽의 부분집합이 아니라서 **PM 인데 화면엔 수정 버튼이 없고 AI 로는 되는** 경우가 실제로 있다.
- 교체하면: 회사가 이미 정한 규칙을 AI 가 따르게 되고 코드가 줄어든다.
  `judgeEditProject` 는 **거부 이유 문구 생성**만 남긴다(그건 화면에 없던 값어치).
- 판단 보류 이유: 화면 권한 정책 자체를 손볼지(영업부 전원이 모든 프로젝트를 고치는 게 맞나)를
  같이 봐야 하는데, 그건 AI 단계가 아니라 조직 정책 문제다.
